# 成稿内容与检查规则

入口的四条要求适用于默认 `project_only` 正式报告。内容模式决定叙述范围，项目阶段决定哪些事实可写；两者不能混用。

## 写作处理

正文围绕实际工程对象说明职责、架构、接口、配置、处理逻辑、设计选择和成果。模型、协议分析、仿真、实物与现场测量分别命名，任何状态都须有资料支持。

缺少实测结果时，写完整的技术原理或设计关系，明确数值是手册参数、配置值、推导值还是协议示例；不填造精度、运行时长、成功率、测试通过或功能完成结论。不将内部缺少记录的项目转成默认成稿的“未完成、待验证、待测、后续补齐”清单。

“未连接、未定位、等待初始化、丢弃残帧”等运行状态可以用于解释状态机与故障处理，它们不表示项目目标未完成。技术叙述按具体对象和条件判断，审计脚本不得按“未、待、后续”单字批量删改。

只有用户明确要求进度汇报、未完成事项或未来计划时使用 `progress`。该模式允许对应范围的进度说明，但仍禁止编造成果、混入写作材料文献或用外部附件代替正文解释。不得因 `project.stage=concept/prototype` 自动切换。

## 资料角色与参考文献

内部资料清单区分以下角色：

| 角色 | 用途 | 是否进入参考文献 |
|---|---|---|
| 排版样例与参考报告 | 章节组织、篇幅、语气与格式 | 否 |
| 写作输入材料 | 项目工程包、会议录像、逐字稿、聊天附件与照片 | 否；来源在内部清单追溯 |
| 项目技术参考 | 芯片手册、接口规范、设计指南、算法论文与核心依赖资料 | 按项目实际引用列出 |

不能把“用于追溯写作输入”当作“属于项目技术文献”。文献条目与正文的具体技术方案或方法对应，普通超链接用于延伸阅读；必要的参数、步骤、处理关系和图表已经在报告中说明。

写作前把样例与写作材料的标题写入 `quality.forbidden_reference_titles`，不要将技术参考加入禁用标题。CLI 可重复传 `--forbid-reference-title`。标题检查兼容版本号和常见文件扩展名的变化，避免只修改样例版本名便漏检。

## 自解释性人工核对

脱离源文件逐章阅读，核对：

- 每个核心模块的输入、处理、输出及与其他模块的关系。
- 缩写、引脚、符号、单位、参数性质及公式的变量含义。
- 示意图、协议示例、仿真与实物各自描述的对象。
- 结果的对象、条件、方法和数值依据；图表与文字一致。
- 参考文献只支持技术引用，正文不要求读者打开会议、附件或样例才能理解关键内容。

这些语义项必须人工完成；关键词和 DOCX 包结构检查不能证明全部技术解释完整。

## 交付检查

默认正式 DOCX 使用：

```bash
python3 <skill-dir>/scripts/audit_docx.py <report.docx> \
  --project-report --check-content-policy --content-profile project_only \
  --require-toc --check-cross-references --check-body-indent --check-self-contained \
  --forbid-reference-title "<写作样例标题>"
```

无禁用标题时省略对应选项；用户明确要求的进度任务改为 `--content-profile progress`。`--project-report` 本身也默认启用内容检查，防止遗漏额外选项导致旧行为复现。

内容检查扫描正文、标题、技术表格、题注、页眉页脚、注释、文档属性和图片替代文本；查验参考文献文字与超链接目标；拦截明确的未完成项目说明、写作过程叙述、写作材料引用和外部内容域依赖。修订记录是历史描述，保持原条目，不按当前正文规则改写历史。图像中的实际文字仍由视觉检查核对。

命中内容错误时返回非零退出码，并列出所在部件、位置、类别和文字。审计为只读操作；Agent 根据对象与上下文修正文档，保持原稿和版本记录，再重新检查。不得将自动删词、空表、模糊措辞或没有资料支持的“全部完成”作为修复。
