# 资料支持程度与写作规则

以下分类只用于内部工作。成稿使用“当前状态、完成范围、测试结果、后续安排”等项目语言，不增加“资料依据”章节或索引。

## 资料与结果分类

### A 类：实现与结果记录充分

包括源码、配置、运行截图、测试记录、输出文件或实物照片，并能相互印证。

可以写：

- 已完成模块实现
- 完成接口联调
- 在指定场景下观察到某项结果

仍不得把单次或局部验证概括为长期稳定运行。

编译日志只能证明工程通过编译，不能证明程序已在硬件上正确运行。界面截图若显示报错、告警、未连接或状态未知，只能作为问题记录或局部界面资料。

### B 类：有实现资料，但结果记录不完整

包括完整源码、模型、图纸或配置，但缺少可核验的系统级测试记录。

建议写：

- 完成该模块的实验性实现
- 搭建实验性方案
- 具备进一步联调基础

不要写准确率、实时性、成功率、稳定性等结论。

### C 类：只有方案或参考资料

只有说明文档、示例工程、论文、教程或计划。

建议写：

- 形成技术路线
- 完成原理分析和方案设计
- 作为后续实现或优化方向

不要写“已实现”“已验证”“已部署”。

## 内部事实清单字段

为每项核心内容记录：

- 报告章节
- 模块或功能
- 资料路径
- 资料类型
- 可支持的事实
- 尚不能支持的结论
- 推荐措辞
- 需要补充的图片或测试

内部事实清单用于写作过程，不作为“资料依据”章节放进成稿。

## 技术内容写法

先写工程对象，再写动作和结果：

- 弱：系统具有较好的智能化水平。
- 强：识别节点接收相机图像，输出类别状态；导航层依据状态决定继续执行或停车等待。

先写接口，再写关系：

- 输入是什么
- 如何处理
- 输出到哪里
- 失败时如何处理

将“设计意图”和“验证结论”分开：

- 设计意图：为降低误识别对运动控制的影响，增加连续帧确认。
- 验证结论：只有存在记录时才说明观察结果；否则写为待后续系统测试。

## 指标审查

遇到以下内容必须回查原始资料：

- 百分比、毫秒、帧率、速度、距离、功耗、误差
- “稳定”“实时”“高精度”“显著提升”
- “达到”“满足”“优于”“成功完成”
- 测试次数、运行时长、数据集规模

无法定位到记录时，删除数字或改为实验性描述。

## 重复资料与测试记录

- 对同名、同尺寸或处于重复目录的源码、模型、图片和文档进行内容比较。
- 内容相同的副本按一项成果统计，不因出现多份而提高资料支持程度。
- 测试表中的“检查方法”“预期结果”属于测试设计；只有实际观察、日志、截图或结论字段才能支持结果判断。
- 示例数据、图库图片和通用演示不能替代真实项目输入或实测结果。

## 编写过程说明清理

以下内容只用于内部工作，不进入项目成稿：

- 资料依据与编写口径
- 文件夹扫描说明
- AI 生成或润色说明
- 自检过程
- 为凑篇幅设置的附录
- 与项目没有直接关系的参考资料列表

若用户或提交机构明确要求参考文献、诚信声明或格式说明，则按其模板保留。
