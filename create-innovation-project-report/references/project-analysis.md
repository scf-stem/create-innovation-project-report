# 项目背景、需求与场景分析

## 背景写法

背景从项目面对的具体问题写起：

1. 使用环境是什么。
2. 现有操作怎样完成。
3. 哪一步耗时、易错、难观察或存在安全风险。
4. 项目怎样处理这一问题。
5. 核心功能在系统中承担什么任务。

避免以“随着科技快速发展”“具有重要意义”“顺应智能化趋势”开头。

## 参与对象

至少区分：

- 日常使用者：关注状态、操作和反馈。
- 安装调试者：关注接线、配置、标定和日志。
- 维护人员：关注拆装、故障和替换。
- 验收人员：关注目标、结果和完成边界。

不同对象看到的信息和完成的任务不同。界面、结构和文档应分别回应这些任务。

## 使用场景

每个场景用“触发条件—用户动作—系统响应—完成标准”描述。

示例：

| 场景 | 触发条件 | 用户动作 | 系统响应 | 完成标准 |
|---|---|---|---|---|
| 环境异常 | 温度超过阈值 | 查看状态或人工干预 | 输出控制并提示 | 状态、动作和记录一致 |

没有正式用户反馈时，不写“用户普遍认为”。默认正式报告直接说明使用流程、操作条件和交互设计；用户明确要求进度任务时，可按 [内容模式规则](content-policy.md) 写任务测试计划。

## 需求分层

- 功能需求：系统要完成什么。
- 性能需求：速度、精度、容量和稳定性。
- 安全需求：失效状态、保护和权限。
- 可维护需求：配置、日志、拆装和替换。
- 交付需求：源码、模型、图纸、数据和文档。
- 功能体系：模块职责、接口配置与输入输出关系。

需求表中的“实现结构”须对应已有工程对象；数据处理设计与实测结果分别命名。默认不将未覆盖目标列入成稿需求表。

## 背景到技术路线的衔接

每项主要需求都要在后文找到设计与验证：

`问题 → 需求 → 方案 → 模块 → 测试 → 结果/边界`

若链条中断，补充说明或删除无支撑的需求。
