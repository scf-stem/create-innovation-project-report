# 技术路线与工程实现叙述

## 技术路线

技术路线回答“为什么这样做、按什么顺序做、各部分怎样连接”。推荐结构：

1. 约束：硬件平台、成本、时间、接口和环境。
2. 备选方案：至少说明主要替代方案。
3. 选择理由：结合本项目约束，不写通用优点堆砌。
4. 实施顺序：原型、单模块、接口、整机和验收。
5. 结果与边界：当前完成状态和后续条件。

## 系统架构

按项目选择合适层级，不固定套用：

- 物理与机械层
- 感知与数据层
- 控制与执行层
- 决策或业务规则层
- 交互与应用层
- 工程资源与运维层

架构图中每条箭头要有含义：数据、控制命令、电源、机械连接或用户操作。正文说明主要数据和控制过程，以及发生异常时的处理过程。

## 模块写法

每个模块说明六项内容：

1. 职责
2. 方案与选择原因
3. 输入
4. 处理与关键配置
5. 输出及接口
6. 测试结果与限制

硬件模块补充电压、电流、引脚、总线、地址、触发电平和保护；软件模块补充线程、周期、状态、异常和资源清理；算法模块补充数据、参数、输入输出和评价方法。

## 开发过程

Git、文件时间和测试脚本可用于还原开发过程。使用直观标题：

- 项目开发过程与阶段成果
- 主要功能完成顺序
- 从原型到整机联调

只保留对工程决策有解释力的阶段，不逐条抄提交记录。说明某次调整解决了什么问题、影响哪些模块、怎样验证。

每个关键阶段按“目标与输入—实际步骤—出现的问题—排查与调整—复测结果—遗留事项”组织，可采用连续段落或过程表。文件时间只用于定位材料，不能单独证明实施或测试发生在该日。无法确认的步骤、工具、接线、样本量和测试结果不补造。

图表与文字共同说明实施过程：结构图解释装配和连接，接口表解释参数及状态，步骤图展示操作，测试表承载条件和结果。图题明确区分方案、实物和测试状态；未验证的设计只写其预期作用。

## 代码片段

代码片段只用于说明：

- 核心算法或公式
- 接口协议
- 状态机和控制边界
- 异常处理和安全关闭

每段尽量控制在 5–15 行。删除导入、样板代码和无关注释。正文先解释目的，再展示片段，随后说明输入输出。

## 功能核对

不能仅凭按钮名称、槽函数或占位配置认定功能可用。核对：

- 界面是否真的显示该控件
- 事件是否绑定
- 后端是否执行
- 硬件对象是否配置
- 是否有运行或测试记录

如果只有动画或模型状态变化，要明确说明物理动作是否执行。
